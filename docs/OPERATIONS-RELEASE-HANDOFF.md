## 이번 계측 변경
- 온보딩에서 실제 일정 저장이 성공한 후 occasion_saved를 기록한다. 예시·실패는 기록하지 않는다.
- 데이터를 읽고 첫 화면을 준비하면 session_started를 기록한다. 세션/일자 집계는 SQL에서 중복 계정과 날짜 기준으로 처리한다. 페이지 재열기 횟수를 사람 수로 세지 않는다.
- 로그인 이벤트는 session_authenticated이다. 로그인 성공을 원 계정·원 기록 복구 성공으로 오인하지 않는다.
- 알림 미루기는 reminder_snoozed이다. 실제 참석/안부 완료와 구분한다.
- 속성은 허용 목록으로 제한한다. 자유 입력 ref·kind·검색어 등도 전송하지 않는다. 서버 제약도 허용 속성만 받는다.
- RLS에서 authenticated 계정은 본인 ID로 이벤트를 넣을 수 있다. 사용자 조회/수정/삭제 권한은 부여하지 않는다. SQL Editor 관리자는 집계 가능하다.
- 이벤트는 클라이언트 보고이므로 위변조 가능성이 있다. 결제·정산·공식 감사 수치의 근거로 사용하지 않는다.

## DB 실행·검증 순서
1. QA DB 백업과 대상 프로젝트 확인 후 migration SQL을 실행한다. 제공 코드만으로 실행 성공을 가정하지 않는다. 기존 app_events가 있다면 먼저 구조·정책을 비교한다. create table if not exists는 기존 구조를 자동 보정하지 않는다.
2. 새 QA 계정으로 앱을 열고 실제 일정/금품을 각각 저장한다. 관리자 쿼리로 ID·이벤트·공통 속성을 확인한다. 예시·실패·알림 미루기가 저장/챙김 성공에 섞이지 않는지 확인한다.
3. 두 QA 계정으로 타인 user_id 삽입이 거부되는지, 사용자 SELECT가 차단되는지, 허용되지 않은 props가 거부되는지 확인한다. 실제 DB에서 실행하기 전까지 RLS 통과로 표시하지 않는다.
4. 운영 프로젝트 적용 시점·최초 계측일·QA 제외 계정을 운영 기록에 남긴다. 90일 초과 이벤트 정리 작업은 운영자가 별도로 스케줄을 설치하고 결과를 확인한다. 현재 자동 삭제가 구현됐다고 표현하지 않는다.
5. 개인정보처리방침의 ‘익명 통계’ 표현은 user_id를 사용하는 가명 측정에 맞춰 정정한다. 계측 목적·보관/삭제 운영을 실제 정책과 맞춘 뒤 출시한다.

## 지표 해석
집계 SQL은 원시 계정 수/분모/분자를 반환한다. 비율은 분자÷분모이고 분모가 0이면 N/A다. QA 제외 UUID는 운영자의 비공개 설정으로 관리한다.

- observed_accounts는 계측 시작 이후 관찰된 계정 수다. 사람 수·전체 가입자 수가 아니다. 기기별 익명 계정, 이메일 연결과 병합의 중복은 아직 정규화하지 않았다.
- 7일 활성화: 첫 관찰 후 7일 이상 지난 계정 중 첫 7일 안에 실제 기록 저장 성공. 계측 이전 가입 시점은 알 수 없어 ‘가입 7일’ 지표로 단정하지 않는다.
- 28일 기록 활성: 첫 관찰 후 28일 이상 지난 계정 중 최근 28일 실제 일정/금품 저장 성공. 원래 목표의 참석/안부·일정 확인을 포함한 넓은 활성 지표의 하위 지표다. 이 값만으로 활성 50% 목표를 판정하지 않는다.
- 28일 기록 재사용: 첫 실제 저장 후 28일 관찰이 끝난 계정 중 한국 날짜로 다른 날, 첫 저장 후 28일 안에 다시 저장한 계정.
- session_started는 방문 추이를 보여준다. 방문만으로 핵심 활성이나 관계 챙김 완료로 간주하지 않는다.
- 저장 성공률은 저장 시도 이벤트/정확한 재시도 귀속이 미구현이므로 계산하지 않는다. 복구 성공률도 원 계정·원 기록 대조가 미구현이다.
- 리뷰 4.5는 실제 스토어 리뷰/리뷰 수와 함께, 50,000명은 중복 제거한 사용자 정의와 함께 별도 보고한다.
